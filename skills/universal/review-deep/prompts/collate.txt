Group code-review findings into issues for component $component of the repository at $checkout, which is your working directory.

The findings are listed below, $count of them, grouped under one "## path" heading per file. Each finding line reads: ID, L<line>, severity, source/area, an optional backticked symbol, then the finding text. The sources are several reviewer models and a scanner. They reviewed the same files independently, so one defect often appears several times in different words, at nearby lines, or once at a caller and once at its callee.

$findings

Grouping rules:
- Two findings belong to one issue when a single code change fixes both. Findings about different defects stay separate issues, even inside one function.
- The same pattern repeated in several places of this component is one issue only when one change fixes every place, such as a shared helper, a middleware, or a config value. Otherwise keep one issue per place.
- Every ID above goes into exactly one issue's members, or into dropped. Never list an ID twice. Never invent an ID.
- Drop a finding only when its own text says there is no defect, for example that a pattern is correct or safe. Doubt about whether a finding is true is not a reason to drop it, because a later step verifies every issue.
- Do not judge whether a finding is true. Read source code only when the text of two findings leaves unclear whether one change fixes both.
- title is one line of at most 15 words naming the defect and the symbol or file it is in.
- location is the path:line where the fix goes, copied from a member finding.

Use keys $component-001, $component-002, and so on.

Do not modify any file.
