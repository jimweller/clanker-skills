Judge and edit one bug ticket. The ticket describes code in the repository at $checkout, which is your working directory. The working tree holds commit $commit, and the files in the working tree are the ground truth for every claim. A claim that rests on a file absent from the working tree is not supported.

The ticket has a Summary and a list of findings. Each finding was written by an engineer about a line in $where.

Summary: $summary

Findings:
$findings

Read the code to judge every claim in every finding. Try to refute each claim first. Look for guards, validation, callers, configuration, framework behavior, and tests that would prevent the described failure, and follow the code across files as far as the claim requires.

Then act as the ticket's editor, finding by finding.
- keep: every claim in the finding holds. Return the text exactly as written. In reason, take the finding's claims one by one and name the code that supports each.
- edit: the finding's central claim holds but part of it does not. Change only what the code contradicts or does not support. Delete a wrong clause or sentence, narrow a claim that reaches too far, or correct a detail the code settles, such as a count, a caller, or a condition. Keep the author's words and voice everywhere else, add nothing the code does not show, and do not rephrase accurate text.
- delete: the finding's central claim does not hold. Return an empty text.
For every edit and delete, give the reason and cite the code that decided it as evidence: path:line and the lines copied exactly from the file. A keep needs no evidence, but its reason must account for every claim.

Write the Summary so it states what the kept and edited findings establish, in at most 80 characters with no trailing period. Return an accurate existing Summary exactly as it is.

verdict is "true" with basis "confirmed" when at least one finding is kept or edited. Otherwise verdict is "false", with basis "refuted" when the code contradicts the findings, or "insufficient_evidence" when they depend on things outside the repository. reason explains the verdict and names the code you read.

Assess severity from the code. Critical is an exploitable security flaw, or data loss or corruption in normal use. High is wrong behavior or an outage risk on a common path. Medium is wrong behavior on an edge case, or a significant maintainability or reliability risk. Low is minor. severity_reason explains it.

Suggested fixes in a finding may stay, and you need not judge them. Accurate words such as vulnerable, fails, or leaks stay. Nothing in the Summary or the finding texts may mention how the defects were found or that the ticket was edited.

Do not modify any file.
